## Rule 3 — Angular best practices

Use modern Angular practices appropriate for the project's Angular version.

Prefer:

* standalone components
* `inject()` where appropriate
* typed forms
* strong TypeScript typing
* `ChangeDetectionStrategy.OnPush` where appropriate
* clean dependency injection
* route guards
* HTTP interceptors
* reusable shared components

Do not introduce NgRx or another state-management library unless there is a genuine requirement.

# 6. TYPESCRIPT RULES

Use strong typing.

Avoid:

```ts
any
```

unless there is a legitimate technical reason.

Prefer:

```ts
interface
type
enum
generic types
union types
```

where they improve clarity.

Use meaningful names.

Avoid unnecessary abbreviations.

Do not create excessively complicated types just to appear "advanced."

The code should be maintainable by a normal Angular developer.

---

# 7. COMPONENT RULES

Components should primarily handle:

* UI state
* user interaction
* form state
* presentation logic

Do not put large business rules inside components.

Move reusable business/API logic into services.

Avoid huge components.

If a component becomes unnecessarily complex, tell me and recommend a clean split.

---

# 8. SERVICE RULES

Services should have clear responsibilities.

Examples:

```text
ApiClientService
    ↓
feature service
    ↓
component
```

Do not make every component directly call `HttpClient`.

The API client should centralize common HTTP behavior.

Feature-specific services should contain feature-specific API operations.

---

# 9. API ARCHITECTURE

Use:

```text
Component
    ↓
Feature Service
    ↓
ApiClientService
    ↓
HttpClient
    ↓
Backend API
```

Do not use:

```text
Component
    ↓
HttpClient
```

unless there is an exceptional reason.

Centralize:

* API base URL
* HTTP behavior
* common error handling
* authentication headers
* response handling

Use environment/configuration values where appropriate.

# 21. CODE STYLE

Use clean formatting.

Use:

* camelCase for variables/functions
* PascalCase for classes/interfaces/components
* meaningful names
* small methods
* clear control flow
* early returns where useful
* strict typing

Avoid:

* unnecessary comments
* clever one-liners
* deeply nested conditions
* duplicated code
* giant methods
* magic numbers
* unexplained constants

# 22. SECURITY

Follow reasonable frontend security practices.

Do not:

* expose secrets in Angular code
* hard-code API credentials
* store sensitive credentials unnecessarily
* trust client-side role checks as backend authorization
* put secrets in environment files that are intended to remain private

Remember:

> Angular authorization improves UX, but backend authorization provides actual security.

* subscriptions

* DOM rendering
* duplicated calculations
* expensive template expressions

Use appropriate Angular patterns for:

* async data
* observable cleanup
* change detection
* list rendering

Do not optimize prematurely.

Keep the code simple first.
